## 二、明天开工第一件事：看懂 VideoWriter

当时为了快点看到结果直接复制了，下面这 5 个点是必须弄懂的。

### 1. 构造函数的四个参数

```cpp
VideoWriter writer("output/result.avi",                 // ① 输出路径
                   VideoWriter::fourcc('M','J','P','G'), // ② 编码器
                   fps,                                  // ③ 帧率
                   Size(width, height));                 // ④ 画面尺寸
```

- **① 路径**：扩展名决定容器格式（`.avi` / `.mp4`）
- **② fourcc**：四个字符的编码标识，`MJPG` 是 Motion-JPEG
- **③ fps**：**必须传源视频的 fps**，否则播放速度会变
- **④ Size**：**宽在前、高在后**，写反会导致写失败或图像错乱

### 2. fourcc 是什么

```text
Four Character Code，四字符编码标识。
VideoWriter::fourcc('M','J','P','G')  →  "MJPG"
VideoWriter::fourcc('m','p','4','v')  →  "mp4v"（MPEG-4 Part 2，体积小很多）
```

不同本机支持情况不同，任务书说"具体编码由本机 OpenCV 支持情况决定，提交时记录"。

### 3. 为什么每帧都要 `writer.write(canva)`

```text
VideoWriter 内部维护一个编码器 + 文件流
每调用一次 write()，就把这一帧编码后追加到文件
不调用 → 文件里就没有这一帧
```

### 4. 为什么最后要 `writer.release()`

```text
编码器有内部缓冲，最后一帧可能还没真正写进文件
release() 会 flush 缓冲 + 关闭文件
不调用 → 文件可能不完整、无法播放
```

**这也是为什么"帧数 4210"能对得上——只有 release 了才算写完。**

### 5. 为什么时长能对上（35.08 秒）

```text
时长 = 帧数 ÷ fps = 4210 ÷ 120 = 35.08 秒
```

因为写入时传的就是源视频的 `fps`（119.998 ≈ 120），所以时长天然一致。

**如果传了错误的 fps（比如 30），帧数不变但时长会变成 140 秒。**

```text

④ while (cap.read(frame))
     ├─ frame.empty() 检查
     ├─ detect_armors(frame)             每帧检测
     ├─ 统计 frames_with_armor / total_armors
     ├─ frame.clone() 得到 canva，画框
     ├─ 每 500 帧存一张 output/frame_N.png
     ├─ writer.write(canva)              写入结果视频
     └─ frame_id++

⑤ writer.release()                       收尾，确保文件完整

⑥ 打印统计：总帧数 / 有检出帧数 / 装甲板总数 / 检出率
```

## 四、今天做的三个关键决策

### 1. 视频帧不做 180° 翻转

```text
原因：任务书要求"用原始尺寸的帧和像素坐标做 PnP"
影响：结果视频是倒的（和输入一致），但这符合"与输入帧顺序一致"
      PnP 用原始像素坐标 + 原始 K，最不容易出错
```

### 2. 相机参数用「参数.md」那一组，不用「姿态解算.md」表格里的

```text
K = [[1781.053454, 0, 510.5751561],
     [0, 1781.686873, 472.9735763],
     [0, 0, 1]]
D = [0.1301456438 之类的那组不要用]

判定依据：
  ① 姿态解算.md 表格里那组 k3=17.43，去畸变后画面被拉成桶形 → 明显不对
  ② 参数.md 那组 k3=0.467，去畸变后画面正常
  ③ 群主后来又补发了 参数.md，属于更正
```

### 3. 明确指定 `CAP_FFMPEG` 后端

```text
原因：本机 OpenCV 曾只有 GStreamer 后端，且缺 AVI 解复用插件
现在已修复（见下一节），但显式指定能避免 OpenCV 自动选到 GStreamer
```

## 五、环境变更记录（重要，别再踩坑）

### 问题

```text
原 OpenCV（D:\opencv_work）编译时 WITH_FFMPEG=OFF，只有 GStreamer 后端，
且 GStreamer 缺 avidemux 插件 → 任何 avi 都打不开。
```

### 尝试 1：直接打开 WITH_FFMPEG=ON（失败）

```text
OpenCV 4.12 编译 cap_ffmpeg.cpp 时，依赖系统的 FFmpeg 9（libavcodec 63），
但以下 API 在 FFmpeg 9 中已被删除：
  avcodec_close
  av_stream_get_side_data
  AVCodec::supported_framerates
→ 编译失败
```

### 最终方案：使用 OpenCV 官方预编译 ffmpeg 封装（成功）

```text
① 下载 opencv_videoio_ffmpeg_64.dll（27MB，MD5 e5c6936240201064b15bcecf1816e8f4）
   浏览器访问：
   https://raw.githubusercontent.com/opencv/opencv_3rdparty/ea9240e39bc0d6a69d2b1f0ba4513bdc7612a41e/ffmpeg/opencv_videoio_ffmpeg_64.dll
② 放到 D:\opencv_work\build\3rdparty\ffmpeg\
③ ffmpeg_version.cmake 由本地生成（LF 换行 + 结尾换行，MD5 8862c87496e2e8c375965e1277dee1c7）
④ 修改 D:\opencv_work\source\3rdparty\ffmpeg\ffmpeg.cmake：
   set(ids BIN32 BIN64 CMAKE)  →  set(ids BIN64 CMAKE)   （去掉 32 位）
   原文件备份为 ffmpeg.cmake.bak
⑤ cmake -DWITH_FFMPEG=ON .  然后 cmake --build . -j 8 --target install
```

**验证结果**

```text

```

**产物位置**
